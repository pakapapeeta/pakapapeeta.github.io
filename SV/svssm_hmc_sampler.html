The SVSSM HMC Sampler Engine

Five functions that turn a target log-posterior into posterior draws: _build_preconditioned_kernel, _trace_preconditioned, _run_window, run_chain_windowed_proper, run_chain.

Fact — visible in the code/comments Inference — reasonable, not provable from this slice
Scope. This document zooms into the sampler. It assumes target_log_prob_fn(theta_raw) → scalar log-posterior already exists (built elsewhere by make_target_log_prob) and that the expensive particle-filter likelihood lives inside it. Everything here is sampler mechanics: TFP kernel plumbing, leapfrog/dual-averaging, and the hand-rolled windowed mass-matrix adaptation.

1 · Summary

These functions implement Hamiltonian Monte Carlo two ways:

  • Vanilla (run_chain, default): TFP HamiltonianMonteCarlo + DualAveragingStepSizeAdaptation, identity mass matrix. One fused sample_chain call (or an eager step-by-step loop when progress logging is on).
  • Windowed adaptive (run_chain_windowed_proper): a hand-rolled, Stan-style warmup that adapts both the step size (dual-averaging) and the mass matrix (inverse posterior covariance), re-estimated in expanding windows, then a frozen sampling phase. Built on three helpers — _build_preconditioned_kernel (constructs the kernel), _trace_preconditioned (reads per-step diagnostics), and _run_window (runs one block and returns the smoothed step size).

Why two? Vanilla is cheap and fine when the posterior is roughly spherical. The windowed sampler exists to handle non-spherical geometry — specifically the (phi, sigma_eta²) correlation ridge (~−0.79 at T=100, per the docstring) — and to dodge a runaway step-size pathology that the naïve monolithic adapter stack suffers from. docstring

2 · How they fit together

3 · _build_preconditioned_kernel

Signature. (target_log_prob_fn, step_size, num_leapfrog, momentum_dist, target_accept_prob, num_adaptation_steps) → kernel. Returns a TFP MCMC kernel: a bare PreconditionedHamiltonianMonteCarlo if num_adaptation_steps is None, else that kernel wrapped in DualAveragingStepSizeAdaptation.

inner = tfp.experimental.mcmc.PreconditionedHamiltonianMonteCarlo(
    target_log_prob_fn, step_size=tf.constant(step_size, f32),
    num_leapfrog_steps=int(num_leapfrog),
    momentum_distribution=momentum_dist)        # <- the mass matrix lives here
if num_adaptation_steps is None:
    return inner                                # sampling phase: frozen step
return tfm.DualAveragingStepSizeAdaptation(inner, num_adaptation_steps, target_accept_prob,
    step_size_setter_fn=..., step_size_getter_fn=..., log_accept_prob_getter_fn=...)

Step-by-step

  • Preconditioning = the mass matrix. Plain HMC uses an identity-covariance momentum; PreconditionedHMC lets you pass any momentum_distribution. Its covariance is the mass matrix M. This is the single hook the whole windowed scheme exploits.
  • None ⇒ bare kernel. During sampling the step size is fixed, so no adaptation wrapper is needed; returning inner directly avoids the wrapper overhead and the extra results layer.
  • Else ⇒ dual-averaging wrap with three custom accessor lambdas (next).

The namedtuple tree (why the lambdas exist)

DualAveragingStepSizeAdaptation must read the current step size to update it and write the new one back — both buried inside the inner kernel's results namedtuple. Because the inner kernel is Preconditioned HMC (one extra wrapper vs plain HMC), the default accessors don't line up, so the code supplies explicit getter/setter/log-accept functions that walk this exact structure: docstring

Why _replace? Namedtuples are immutable, so the setter builds a new results tuple with the step size swapped — functional update, not mutation. Fragility: these lambdas are coupled to TFP's exact results layout; a TFP version that renames a field or adds a wrapper layer breaks them. This is the single biggest version-coupling risk in the sampler.

Complexity O(1) construction. Edge case: passing num_adaptation_steps=0 (vs None) would still build the adapter but with zero adaptation — the code uses None as the "no adapt" sentinel, so callers must honor that distinction (and _run_window does).

4 · _trace_preconditioned(_, kr)

A trace_fn is called by sample_chain every step with the (new state, new kernel-results); whatever it returns is collected into the per-step trace. This one returns (accepted, log_prob, step_size) and is written to work for both kernel layerings:

if hasattr(kr, "new_step_size"):        # adapted: DualAveraging is the outer layer
    step = kr.new_step_size
    mh   = kr.inner_results             # peel one layer to the MH results
else:                                   # bare PreconditionedHMC (sampling phase)
    mh   = kr
    step = mh.accepted_results.step_size
return mh.is_accepted, cast(mh.accepted_results.target_log_prob), cast(step)
  • Duck-typing probe. Only the dual-averaging wrapper exposes new_step_size; its presence distinguishes "adapted" from "bare". This lets one trace function serve both warmup (adapted) and sampling (bare) windows, which is why _run_window can pass _trace_preconditioned unconditionally.
  • Why new_step_size for the adapted case but accepted_results.step_size for the bare case? In the adapted wrapper the "current" step is the freshly-proposed one (new_step_size); the bare kernel has no such field, so we read the frozen step from the inner results.
  • tf.cast(..., float32) normalises dtypes so the collected trace arrays are uniform.

Complexity O(1) per step. Edge case: relies on the attribute names new_step_size, is_accepted, accepted_results, target_log_prob being stable across TFP versions (same coupling risk as §3).

5 · _run_window — one block of HMC

Signature. (target, init_state, num_steps, step_size, num_leapfrog, momentum_dist, target_accept_prob, adapt_step_size, seed) → (final_state, samples, acc, lp, step_arr, final_step). This is the atom the windowed sampler composes: run num_steps HMC steps from init_state, optionally adapting the step size, and report the smoothed final step.

num_adapt = int(num_steps) if adapt_step_size else None   # None ⇒ bare kernel
kernel = _build_preconditioned_kernel(..., num_adaptation_steps=num_adapt)
# warmup branch:
samples, (acc, lp, step_arr), final_kr = tfm.sample_chain(
    num_results=num_steps, num_burnin_steps=0, current_state=init_state,
    kernel=kernel, trace_fn=_trace_preconditioned, seed=seed,
    return_final_kernel_results=True)

The smoothed-step logic (the subtle part)

try:
    arr = np.asarray(tf.exp(final_kr.log_averaging_step).numpy())
    smoothed = float(arr.flatten()[0]) if arr.size > 0 else 0.0
except (AttributeError, ValueError):
    smoothed = 0.0
final_step = smoothed if smoothed > 0.0 \
             else float(np.asarray(step_arr[-1].numpy()).flatten()[-1])
Why exp(log_averaging_step) and not the last new_step_size? comment Nesterov dual-averaging keeps two quantities: a fast-moving new_step_size (noisy) and a slow running average log_averaging_step (smoothed) — the latter is what Hoffman & Gelman recommend and what Stan reports as the final step. In short windows the fast value hasn't settled, so the smoothed average is far more robust. The try/except + >0 guard falls back to the last traced step if the field is missing or zero (defensive against TFP shape/version quirks).
  • num_burnin_steps=0 on purpose: warmup is managed externally by the windowing loop, not by sample_chain — every step is kept so the window's samples can be used to estimate the mass matrix.
  • Non-adapt branch: final_step = float(step_size) — the input is returned unchanged because sampling freezes it; step_arr isn't even read.
  • final_state = samples[-1] threads the chain's last position into the next window so windows are continuous (no re-initialisation between them).

Complexity O(num_steps × L × cost(target)). Edge cases: the nested .numpy().flatten()[-1] guards scalar-vs-array shape ambiguity in the traced step; tf.exp of a missing field is caught by the except.

6 · run_chain_windowed_proper — the warmup engine

This is the centerpiece. It schedules warmup as init → 3 expanding windows → (frozen) sampling, adapting step size in every warmup window and the mass matrix at the end of all but the last.

Window budget

phase1_n     = max(int(B*0.10), 5)        # init window
phase2_total = max(B - phase1_n, 18)
w1 = max(phase2_total // 8, 4)
w2 = max(phase2_total // 4, 6)
w3 = max(phase2_total - w1 - w2, 8)       # the "super-window"
Key design — no separate "term" phase. comment Stan normally ends warmup with a short fixed-mass "term" window where the step size settles against the final mass matrix. Here the last expanding window IS the term window: W3 does not update the mass at its end, so the step size it adapts is already tuned against the exact mass matrix sampling will use. The docstring records why a separate short term phase failed: the mass changed at term-start, forcing the step to re-equilibrate with only ~8–16 steps left — not enough for dual-averaging to settle, so one chain landed at a locally-OK but sampling-bad step. Enlarging W3 to absorb the term role fixes that.

The max(..., floor) guards keep windows usable even when num_burnin is tiny (degrades adaptation quality but never crashes). Note the docstring says "1:2:4" / "1:2:5" while the code yields roughly 1:2:5 from //8, //4, remainder — a minor doc/code drift worth flagging in review.

Mass-matrix math — the crux

Convention: mass matrix M := Σ⁻¹ (inverse posterior covariance). The momentum distribution's covariance is set to M = precision, not Σ. The leapfrog position update q += eps · M⁻¹ · p then scales by Σ, so high-variance directions take proportionally larger steps. This "sphericises" the geometry. docstring/comment

The docstring explicitly records a fixed bug: "v4 passed sample variance directly as momentum scale² — wrong direction", masked only because all three SVSSM params have similar posterior scale. Correct direction = precision, derived below.

Diagonal mode

var = clip(reduce_variance(win, axis=0), 0.1, 10.0)
precision_diag = 1.0 / var
momentum = Independent(Normal(0, sqrt(precision_diag)))   # scale = sqrt(M)

Dense mode (default)

cov = covariance(win) + 1e-4·I            # ridge for a stable eigh
cov = symmetrise(cov)
e, v = eigh(cov);  e_clip = clip(e, 0.1, 10.0)            # bound EIGENVALUES
cov_clip = v · diag(e_clip) · vᵀ ;  symmetrise
precision = symmetrise( inv(cov_clip) )
momentum = MultivariateNormalTriL(scale_tril = cholesky(precision))   # cov = M
Why eigen-clip, not entry-clip? comment Clipping eigenvalues to [0.1, 10] bounds the per-direction scale while preserving the eigenvectors — i.e. it keeps the correlation structure (the phi–σ² ridge) but prevents any direction's variance from collapsing to ~0 (which would make precision, and thus leapfrog trajectory length, explode — the "briefly-stuck-chain" pathology). Identity mass ≡ var 1, so [0.1, 10] permits a 10× rescale either way. Note for MVNTriL: scale_tril must be the Cholesky of the distribution covariance, which here equals the precision — so we feed cholesky(precision) directly.

Why reset the step-size adapter at each window boundary? docstring A monolithic DualAverage[DiagonalMass[PHMC]] stack runs two adapters that update independently every step; they can co-amplify and drive the step size to inf on bad geometry. Building a fresh dual-averaging kernel per window (each _run_window call constructs a new kernel) breaks that feedback loop. This is the core reason the function is hand-rolled instead of using TFP's built-in DiagonalMassMatrixAdaptation.

The warmup loop, step by step

  1. Init momentum = identity mass (dense: I; diag: ones).
  2. Init window: _run_window(adapt=True); clip eps ∈ [1e-4, 0.3].
  3. For each of W1, W2, W3: run with current mass + step-size adapt; clip eps; if not the last window, take the window's post-burn samples (skip = max(25%·wsize, 1)), estimate precision, rebuild the momentum distribution. Log diag-variance and (dense) max |correlation|.

Step-size cap rationale comment: capped to [1e-4, 0.3] (not 0.5). The comment records that eps=0.5 + frozen-mass sampling gave <5% acceptance on 2/4 chains in a 72-min laptop test; the 0.3 cap keeps every chain productive. (There's a doc/code drift here too: a comment mentions "target_accept 0.8" but the effective default is 0.65 — see §7.)

Chunked sampling phase

chunk_size = clamp(progress_every or num_results, 1, num_results)
while samples_done < num_results:
    this_chunk = min(chunk_size, num_results - samples_done)
    state, samp_c, acc_c, lp_c, _, _ = _run_window(..., adapt_step_size=False,
        seed = seed + 1_234_567 + chunk_idx*7919)   # distinct stream per chunk
    ... accumulate; print heartbeat with ETA ...
samples = concat(chunks); acc = concat; lp = concat
  • Why chunk? comment So the run emits heartbeat lines (with running acceptance + ETA) during sampling, which at high T can be hours. With progress_every == 0 it's a single chunk (silent).
  • Frozen everything: adapt_step_size=False and the same momentum across chunks ⇒ a single homogeneous Markov chain split only for logging; concatenating the chunks is valid because the transition kernel is identical.
  • Synthesised step array: since the step is frozen, the function returns np.full(num_results, current_step) rather than the traced array — the comment notes the bare-kernel trace can have inconsistent shape.

Returns NumPy arrays (samples, acc, lp, step_arr) — matching run_chain's vanilla return so callers are agnostic to which sampler ran.

Complexity O(total_steps × L × cost(target)); the per-window 3×3 eigh/inv is negligible. Memory O(draws × d) plus transient per-window blocks. Edge cases: tiny windows → noisy mass estimate; non-PSD window covariance handled by the ridge + eigen-clip; skip can leave very few samples for the estimate in small windows.

7 · run_chain — the dispatcher

Signature. (target, init_raw, num_results, num_burnin, step_size, num_leapfrog, seed, target_accept_prob=None, progress_every=0, use_windowed_adaptive=False, dense_mass=True) → (samples, acc, lp, step) as NumPy.

If use_windowed_adaptive, forward to run_chain_windowed_proper with default target_accept_prob = 0.65. Otherwise build the vanilla stack:

kernel = tfm.HamiltonianMonteCarlo(target, step_size, num_leapfrog_steps)
kernel = tfm.DualAveragingStepSizeAdaptation(kernel,
            num_adaptation_steps=num_burnin, target_accept_prob=0.65)
Doc/code drift to flag in interview/review. Two comments here say the vanilla branch is "less conservative than the windowed branch's 0.80", but the windowed branch's actual default is 0.65 (set in this same function). The earlier 0.80 target was tried and reverted — the comments are stale. Substance: both branches default to target_accept_prob = 0.65 (Hoffman & Gelman's fixed-L recommendation). code vs comment

The robust trace_fn

inner = kr
while hasattr(inner, "inner_results"):     # drill through ALL wrapper layers
    inner = inner.inner_results
accepted = cast(inner.is_accepted) if hasattr(inner, "is_accepted") else False
lp = inner.target_log_prob if hasattr(inner, "target_log_prob") \
     else inner.accepted_results.target_log_prob if hasattr(...) else nan
step = kr.new_step_size if hasattr(kr, "new_step_size") else nan

Unlike _trace_preconditioned (which knows it's exactly one or zero wrappers), this one loops through arbitrarily many inner_results layers and uses hasattr fallbacks for every field — maximally defensive, because the vanilla stack's layer count can vary. Reads the step from the outermost new_step_size (the adapter), not the inner results.

Complexity O((burnin+results) × L × cost(target)). Edge cases: the two paths use different RNG conventions (scalar vs 2-vector seed), so results are not bit-identical between them — a reproducibility gotcha if you compare logged vs silent runs.

8 · Seed discipline

Seeding is deliberately structured so windows and chunks draw from distinct streams while staying reproducible:

SiteSeedWhy
init windowseedBase stream.
warmup window wiseed + 10_000·(wi+1)Large stride so windows don't overlap streams.
sampling chunk kseed + 1_234_567 + k·7919Offset + prime stride ⇒ decorrelated, reproducible chunk streams.
vanilla loop step s[seed, s+1]Stateless 2-vector seed (TFP "stateless" RNG convention).
Interaction with the target's CRN seed. inference The target log-prob (in the full file) resets a global seed each evaluation to make the particle-filter estimate deterministic in theta. That is independent of these sampler seeds, which drive the momentum draws and MH accept coin. So: momentum/accept randomness varies per step (good mixing), while the likelihood surface is fixed per theta (energy conservation). The two seed systems serve orthogonal purposes.

9 · Complexity & memory

  • Time: every path is O(#steps × L × cost(target)). The target is the bottleneck (one filter pass per leapfrog step); all sampler bookkeeping is rounding error.
  • Linear algebra: dense mass adds one eigh + inv + cholesky on a d×d matrix per window. Here d=3 ⇒ trivial; would matter at high d.
  • Memory: O(draws × d) for the returned samples + transient per-window/per-chunk blocks. The fused vanilla path is most memory-frugal (TFP streams internally); the eager progress path holds Python lists of per-step tensors.
  • Allocation hotspots: a fresh autodiff graph per leapfrog gradient (freed each step); a new kernel object per _run_window call (cheap).

11 · Modification guide

  • Add NUTS: add a branch in run_chain using tfm.NoUTurnSampler + DualAveragingStepSizeAdaptation; the trace_fn drill loop already handles extra layers. Drop L (NUTS picks trajectory length itself).
  • Swap dense estimator: only dense_precision_from_window needs to change (e.g. Ledoit–Wolf shrinkage instead of eigen-clip); the momentum factory is untouched.
  • Change window schedule: edit the phase1_n/w1/w2/w3 block. Keep the invariant: last window must not update mass (it's the term window).
  • Generalise dimension: nothing here hardcodes d=3 (it reads state_dim = init.shape[0]) — except the d_vec[0..2] logging strings, which assume 3. Fix those to loop for general d.
  • De-fragilise TFP coupling: wrap the getter/setter/trace plumbing in one adapter with a version guard so a TFP bump touches one place.
  • Unify RNG: make both run_chain paths use the same seed convention for reproducible parity.

30 seconds

The interesting one is a hand-rolled Stan-style windowed warmup: init window, three expanding windows that adapt step size (dual-averaging) and re-estimate the mass matrix as the clipped inverse posterior covariance, then frozen sampling. The mass = precision convention and a 'last-window-is-the-term-window' trick are the two non-obvious ideas."

2 minutes

"_run_window is the atom: it builds a PreconditionedHMC kernel (mass matrix = the momentum distribution's covariance), optionally wraps it in dual-averaging, runs sample_chain, and returns the smoothed step from log_averaging_step. run_chain_windowed_proper chains five of these: identity-mass init, then W1/W2/W3 each continuing from the prior state. After W1/W2 it estimates precision — diagonal as 1/clip(var), dense via eigen-clipping the covariance then inverting — and rebuilds the momentum. W3 freezes the mass so its step converges against exactly what sampling uses. A fresh dual-averaging kernel per window prevents the runaway step-size co-amplification the monolithic stack has. Sampling runs frozen, chunked for heartbeat logging, then concatenated. The _build_preconditioned_kernel getter/setter lambdas exist because PreconditionedHMC adds a results layer the default adapter accessors don't expect."

15 · Cheat sheet

_build_preconditioned_kernelPreconditionedHMC; +DualAveraging if adapting. Custom getter/setter for the extra results layer.
_trace_preconditioned(accepted, logp, step) for adapted & bare kernels via new_step_size probe.
_run_windowRun one block; return smoothed step (exp(log_averaging_step)).
run_chain_windowed_properinit + W1/W2/W3 + frozen sampling; mass=Σ⁻¹; eigen-clip; per-window adapter reset; W3=term.
run_chainDispatch windowed vs vanilla(+DualAveraging); robust drill trace_fn; fused vs eager path.

Things most likely to be probed

  • Mass matrix = inverse covariance (and the v4 wrong-direction bug).
  • Eigen-clip preserves eigenvectors, bounds eigenvalues.
  • Last window doubles as the term window (no separate term phase).
  • Per-window adapter reset prevents eps→inf co-amplification.
  • Smoothed log_averaging_step > noisy last step.
  • The getter/setter lambdas exist because of the extra PreconditionedHMC results layer.

Issues worth raising in a review

  • Stale comments: "0.80" target and "1:2:4" ratio don't match the code (0.65, ~1:2:5).
  • TFP version coupling: getter/setter/trace assume a fixed results layout.
  • RNG non-parity between the two run_chain paths.
  • d_vec[0..2] logging hardcodes d=3 even though the rest is dimension-general.
